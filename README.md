# Дообучение компактной VLM для русскоязычного VQA
Выполнил: Ефремов Максим Дмитриевич(МГТУ им. Баумана)

Проектная задача VK «Vision-Language Modeling»: обучить собственную визуально-языковую
модель (Vision-Language Model, VLM) на открытых данных и измерить её качество на
бенчмарках `GQA-ru` и `MMBench-ru`.

Базовая модель [`deepvk/llava-gemma-2b-lora`](https://huggingface.co/deepvk/llava-gemma-2b-lora)
дообучена методом QLoRA (4-bit NF4 + LoRA) на датасете
[`deepvk/GQA-ru`](https://huggingface.co/datasets/deepvk/GQA-ru) в бесплатном Google Colab
(Tesla T4, 16 ГБ). Проведено сравнение базовой и дообученной модели с доверительными
интервалами, проверкой статистической значимости и контрольным экспериментом на формат
промпта.

## Главный результат

Дообучение не изменило точность модели в пределах разрешающей способности эксперимента. Верхние границы доверительных интервалов ограничивают возможный эффект: он не превышает 3.0 п.п. на MMBench-ru и 1.2 п.п. на GQA-ru. То есть заметного прироста, ради которого стоило бы дообучать модель, здесь нет — а если какой-то эффект и существует, он мал. В корректном режиме промпта:
   GQA-ru −0.4 п.п. (p = 0.712), MMBench-ru +1.1 п.п. (p = 0.305). Это ожидаемо для
   `GQA-ru`, train-сплит которого базовая модель уже видела при instruction tuning.
Первоначально наблюдавшийся прирост в +9.9 п.п. на `MMBench-ru` оказался артефактом
(artifact) формата: он исчезает, если добавить в промпт служебный токен `<bos>`,
которого не хватало базовой модели.

Что дообучение действительно дало — устойчивость к формату промпта. Базовая модель
меняет точность на 4–10 пунктов в зависимости от наличия `<bos>`, дообученная
почти не реагирует.

По ходу работы найдены и устранены две ошибки измерения, каждая из которых сама по себе
привела бы к неверному выводу: баг генерации, обнулявший метрику на `GQA-ru`, и
смешивающий фактор (confounder) — формат промпта.

Подробный технический отчёт: [`docs/REPORT.md`](docs/REPORT.md).
Дневник экспериментов: [`docs/EXPERIMENTS.md`](docs/EXPERIMENTS.md).

## Цель и задачи

**Цель:** установить, достижим ли прирост метрик компактной русскоязычной VLM на
бенчмарках `GQA-ru` и `MMBench-ru` средствами QLoRA-дообучения на открытых данных
при ресурсах бесплатного Google Colab, и получить статистически обоснованный ответ
на этот вопрос.

**Задачи:**

1. Развернуть окружение для обучения VLM на GPU с 16 ГБ видеопамяти.
2. Загрузить и подготовить открытый датасет `deepvk/GQA-ru`.
3. Настроить пайплайн QLoRA-дообучения (`transformers` + `peft` + `bitsandbytes`).
4. Обучить LoRA-адаптер поверх языковой части модели.
5. Измерить качество базовой и дообученной модели с доверительными интервалами и
   проверкой значимости различий.
6. Отделить реальный эффект дообучения от эффекта формата промпта.
7. Задокументировать решение, ограничения и воспроизводимость.

**Ожидаемый результат:** обученный LoRA-адаптер, воспроизводимый код и
статистически обоснованный вывод о том, изменилось ли качество модели, — включая
случай, когда вывод отрицательный.

## Данные и как именно они использовались

Все данные — открытые, из коллекции
[deepvk/vision-language-modeling](https://huggingface.co/collections/deepvk/vision-language-modeling).

### `deepvk/GQA-ru` — обучение и оценка в домене

Датасет хранится четырьмя конфигурациями, в которых изображения и вопросы лежат в
разных таблицах и связываются по полю `imageId` (таблица вопросов) ↔ `id` (таблица
изображений):

| Конфигурация | Объём | Как использована |
|---|---|---|
| `train_balanced_images` | 27 519 изображений | источник картинок для обучения |
| `train_balanced_instructions` | 40 000 вопросов | пары «вопрос — однословный ответ» |
| `testdev_balanced_images` | 398 изображений | оценка |
| `testdev_balanced_instructions` | 12 216 вопросов | оценка, метрика Exact Match |

Перед обучением строился индекс `imageId → позиция в таблице изображений`. Из train-сплита
бралась случайная подвыборка в 4000 примеров (`seed=42`). Каждый пример собирался в
формате, повторяющем оригинальное обучение базовой модели: изображение + вопрос +
пост-промпт `«Ответь одним словом.»`, целевой ответ — поле `answer` (одно слово). Промпт
маскировался в `labels` значением `-100`, так что функция потерь считалась только по
токенам ответа.

Поля `fullAnswer`, `semantic`, `annotations`, `groups` не использовались.

### `deepvk/MMBench-ru` — оценка обобщения

Русскоязычная версия MMBench, dev-сплит, 3910 вопросов с вариантами ответа `A/B/C/D`
(у части вопросов заполнены только два варианта, остальные содержат `nan`; у части есть
поле `hint`). Использован только для оценки, в обучении не участвовал: это
экзаменационный бенчмарк, и обучение на нём было бы утечкой (data leakage).

## Метод

| Параметр | Значение |
|---|---|
| Базовая модель | `deepvk/llava-gemma-2b-lora` (LLaVA поверх `google/gemma-2b-it`) |
| Квантование | 4-bit NF4, двойное квантование, compute dtype fp16 |
| Не квантуются | `vision_tower`, `multi_modal_projector`, `lm_head` |
| LoRA | r=16, α=32, dropout=0.05, только `language_model.*` (q/k/v/o/gate/up/down_proj) |
| Обучаемых параметров | 19 611 648 из 2 835 718 144 — 0.69% |
| Обучающая выборка | 4000 примеров, 1 эпоха |
| Batch | 2 × grad_accum 8 = эффективный 16 → 250 шагов оптимизатора |
| Оптимизатор | `paged_adamw_8bit`, LR 2e-4, cosine, warmup 3% |
| Прочее | gradient checkpointing, fp16, `max_length=700` |
| Оборудование / время | Tesla T4 (Colab Free), 60.5 минут |

Визуальный энкодер (vision encoder) и проектор полностью заморожены — адаптируется только
языковая часть. Это стандартный подход, когда задача состоит в адаптации под язык и формат
ответа, а не в улучшении самих визуальных признаков.

Одна картинка разворачивается процессором в 576 токенов-плейсхолдеров `<image>`
(CLIP 336×336, patch_size=14 → (336/14)² = 576) плюс один дополнительный токен. Поэтому
`max_length` не может быть меньше ~600, иначе процессор обрезает часть токенов картинки и
падает с несовпадением их числа.

## Воспроизведение

Окружение — Google Colab, Runtime → Change runtime type → T4 GPU.

Версии закреплены намеренно, произвольные свежие версии ломают пайплайн (см.
`requirements.txt`):

```
transformers>=4.46,<5     # в v5 регресс bitsandbytes 4-bit + device_map="auto":
                          # lm_head теряет quant_state
pillow<12,>=10.0.0        # в Pillow 12.0+ PIL/ImageDraw.py тянет несуществующее имя
                          # _Ink из PIL._typing и ломает `import peft`
```

Фактические версии на момент прогонов: transformers 4.57.6, peft 0.19.1, torch 2.11.0+cu128,
datasets 5.0.0, accelerate 1.14.0.

Дополнительно после загрузки модели вручную проставляются атрибуты процессора
(`patch_size`, `vision_feature_select_strategy`, `num_additional_image_tokens`) — в
`processor_config.json` чекпоинта их нет, потому что он сохранён до появления этих полей,
и без них `LlavaProcessor` падает.

**Порядок запуска:** `01_train_lora.ipynb` целиком → адаптер сохраняется в `adapter/` →
`02_eval.ipynb` целиком. Либо сразу `02_eval.ipynb` с готовым адаптером из архива:
он сам смонтирует Drive, найдёт `adapter_config.json`, прогонит проверку на 20 примерах
и только потом запустит полную оценку.

## Методика оценки

Обе модели оцениваются в одном процессе: дообученная — как есть, базовая — через
`model.disable_adapter()`. Это гарантирует идентичность всего остального пайплайна и
экономит память.

- **Выборки:** по 1000 случайных примеров на каждый бенчмарк, `seed=42`. Все четыре
  конфигурации (`модель × режим промпта`) идут по одним и тем же индексам, то есть
  все сравнения парные (paired).
- **Генерация:** жадная (greedy, `do_sample=False`), `model.eval()`, KV-кэш включён,
  gradient checkpointing выключен, батчи по 8 с левым паддингом. 0.56 с на пример.
- **GQA-ru:** Exact Match — первое слово ответа в нижнем регистре без пунктуации должно
  совпасть с эталоном.
- **MMBench-ru:** в промпт идут `hint` (если есть), вопрос, непустые варианты и инструкция
  ответить одной буквой; из ответа берётся первая допустимая буква. Если модель не выдала
  ни одной — ответ считается неверным.
- **Доверительные интервалы:** бутстрап (bootstrap) по примерам, 10 000 итераций, 95%.
- **Значимость:** парный бутстрап плюс точный тест Макнемара (McNemar's test).
- **Базовый уровень случайного угадывания (random baseline) для MMBench:** усреднённая
  вероятность `1 / (число вариантов)`, на нашей выборке — 26.7%.

### Два режима промпта

Chat template этого чекпоинта не вставляет `<bos>`. Поэтому режим промпта вынесен
в отдельный измеряемый фактор:

- без BOS (`add_special_tokens=False`) — режим, в котором обучался адаптер;
- с BOS (`add_special_tokens=True`) — штатный режим Gemma, соответствующий примеру
  использования из карточки модели.

Обе модели измерены в обоих режимах. Без этого контроля эффект дообучения неотделим от
эффекта формата.

### Разбор ответа на MMBench: почему выбран мягкий парсер

Авторы модели измеряли качество через `lmms-eval` и явно отмечают, что **не использовали
OpenAI API** для извлечения буквы из сгенерированной строки, из-за чего их метрика
сводится к строгому Exact Match по всей строке: засчитывается только ответ, целиком
совпавший с буквой.

Мы сознательно выбрали другой протокол — явная инструкция ответить одной буквой плюс
извлечение первой допустимой буквы из ответа. Причина в том, какой вопрос мы измеряем.

Строгий протокол смешивает две разные способности: понимает ли модель изображение и
умеет ли она выдать ответ в требуемой форме. Для лидерборда это допустимо — там важен
итоговый пользовательский результат. Для нашей задачи — нет: **наш адаптер обучался
именно на форме ответа**, на однословных ответах GQA. Под строгим протоколом его
преимущество, вероятнее всего, выросло бы, и мы бы приписали дообучению улучшение
понимания там, где изменилась только краткость.

Мягкий парсер убирает фактор формата из измерения и оставляет содержательную часть.
Именно поэтому он позволил увидеть то, что видно в разделе «Результаты»: в корректном
режиме промпта дообучение не меняет способность модели отвечать по существу.

Цена этого решения — несопоставимость с опубликованными 40.19: наши 63–64% и их число
измеряют разные вещи. Цена заплачена осознанно. Опорой при чтении наших чисел служит
базовый уровень случайного угадывания 26.65%, а не опубликованное число.

Решение проверяемо: в `results/predictions_mmbench.csv` и `predictions_bos_sweep.csv`
сохранена колонка `raw` с сырой генерацией, поэтому строгую метрику можно пересчитать
офлайн, без модели и без GPU.

## Результаты

### Опубликованные VK результаты (для контекста)

Таблица с карточки модели `deepvk/llava-gemma-2b-lora`, измерения через `lmms-eval`:

| Модель | GQA | GQA-ru | MMBench | MMBench-ru |
|---|---|---|---|---|
| `deepvk/llava-gemma-2b-lora` (наша база) | 56.39 | 46.37 | 51.72 | 40.19 |
| `Intel/llava-gemma-2b` | 59.80 | 0.20 | 39.40 | 28.30 |
| `deepvk/llava-saiga-8b` | 62.00 | 51.44 | 64.26 | 56.65 |
| `llava-hf/llava-1.5-7b-hf` | 61.31 | 28.39 | 62.97 | 52.25 |
| `llava-hf/llava-v1.6-mistral-7b-hf` | 64.65 | 6.65 | 67.70 | 48.80 |

Строка `Intel/llava-gemma-2b` показывает, зачем вообще нужна русскоязычная адаптация:
у англоязычной модели той же архитектуры на `GQA-ru` получается 0.20 против 46.37.

### Кривая обучения

Функция потерь: 6.02 на первом залогированном шаге → 0.49 на последнем
(`results/loss_curve.png`), среднее по всем 250 шагам — 0.8881. Резкое падение приходится
на первые ~20 шагов: это освоение формата ответа, а не приобретение новых визуальных
способностей. Дальше 230 шагов loss колеблется в коридоре 0.53–0.77 без выраженного тренда.

Доля токенов, участвующих в лоссе, — 0.003, около 2 токенов из 600: ответы в GQA
однословные, поэтому обучающий сигнал крайне разреженный.

### Основная таблица: модель × режим промпта

n = 1000 на конфигурацию, интервалы — 95% бутстрап, p — точный тест Макнемара.

| Модель | GQA-ru, без BOS | GQA-ru, с BOS | MMBench-ru, без BOS | MMBench-ru, с BOS |
|---|---|---|---|---|
| `deepvk/llava-gemma-2b-lora` (база) | 35.4 ± 3.0% | 39.6 ± 3.0% | 52.7 ± 3.1% | 63.2 ± 3.0% |
| + наш LoRA-адаптер | 37.9 ± 3.0% | 39.2 ± 3.0% | 62.6 ± 3.0% | 64.3 ± 3.0% |
| Эффект дообучения | +2.5 п.п., p = 0.058 | −0.4 п.п., p = 0.712 | +9.9 п.п., p < 0.001 | +1.1 п.п., p = 0.305 |

Базовый уровень случайного угадывания на `MMBench-ru` — 26.7%.

### Эффект формата промпта

Та же таблица, прочитанная по другой оси: насколько каждая модель зависит от наличия
`<bos>`.

| | GQA-ru, база | GQA-ru, LoRA | MMBench-ru, база | MMBench-ru, LoRA |
|---|---|---|---|---|
| Δ (с BOS − без BOS) | +4.2 п.п. | +1.3 п.п. | +10.5 п.п. | +1.7 п.п. |
| p (Макнемар) | 0.008 | 0.275 | < 0.001 | 0.060 |

### Как это читать

**Прирост от дообучения был артефактом формата.** В режиме без BOS дообученная модель
выигрывала у базовой 9.9 пункта на MMBench (p < 0.001). В штатном режиме с BOS
преимущество падает до 1.1 пункта и перестаёт быть значимым. На GQA-ru эффект и вовсе
меняет знак: +2.5 п.п. без BOS против −0.4 п.п. с BOS (обе величины не значимы).

**Причина видна во второй таблице.** Базовая модель сильно зависит от `<bos>`: без него
она теряет 4.2 пункта на GQA и 10.5 пунктов на MMBench, оба эффекта значимы. На
контрольной картинке без BOS она вырождается в повтор инструкции вместо ответа.
Дообученная модель к формату почти безразлична: +1.3 и +1.7 пункта, ни один эффект не
значим. То есть первоначальное сравнение измеряло базовую модель вне её штатного режима.

**Что дообучение действительно дало — устойчивость к формату.** Адаптер, обученный на
однословных ответах без BOS, снял зависимость модели от наличия служебного токена.
Точность при этом не выросла: в корректном режиме обе модели дают примерно одинаковый
результат (39.6 против 39.2 на GQA, 63.2 против 64.3 на MMBench).

**Почему прироста на GQA нет — объяснимо.** Авторы базовой модели уже использовали
train-сплит `GQA-ru` с тем же пост-промптом «Ответь одним словом.» на этапе instruction
tuning — это прямо указано в карточке модели. Дообучение на данных, которые модель уже
видела, — это дообучение в потолок. Отрицательный результат информативен: рост метрик
требует других данных или другой базовой модели, а не большего числа шагов на тех же
данных.

### Качественные примеры

`results/qualitative_bos.png` — три примера, каждый с четырьмя ответами
(база / LoRA × без BOS / с BOS).

**Открытый вопрос «Опиши картинку несколькими словами».** Без BOS базовая модель
возвращает перефразированную инструкцию вместо описания; с BOS даёт корректное описание
стоп-знака. Дообученная модель отвечает по делу в обоих режимах. Это тот самый признак,
по которому и была замечена проблема формата.

**«Из какого материала сделан знак стоп?»** (эталон «металл»). Без BOS база отвечает
«из бетонного материала» — описывает мусорный бак на переднем плане вместо знака; LoRA
отвечает «металл». С BOS обе модели правы.

**«Салфетка сделана из ткани или бумаги?»** (эталон «бумага»). Без BOS права база, а
LoRA ошибается; с BOS обе отвечают «ткань» и обе неправы. Пример подобран специально:
подборка только из побед LoRA противоречила бы нулевому совокупному эффекту.

### Разбор ошибок

Топ эталонных ответов, которые дообученная модель не угадывает на GQA-ru (режим без BOS):

```
нет 85 | да 60 | стул 9 | справа 9 | слева 9 | девочка 6 | мужчина 6 | стол 6 | белый 6 | плита 6
```

**Около четверти всех ошибок приходится на бинарные «да»/«нет».** Пары «справа» / «слева»
по 9 промахов — путаница лево/право, известная слабость CLIP-энкодеров: LoRA поверх
языковой части исправить её не может в принципе, информация теряется на этапе визуального
кодирования.

Доля пустых ответов — 0.000: модель всегда что-то отвечает, потерь на парсинге нет.

MMBench-ru в разрезе числа вариантов ответа (режим без BOS): 2 варианта — 67.3% (49
вопросов), 3 варианта — 49.0% (51), 4 варианта — 63.1% (900). Провал на трёхвариантных
при 51 наблюдении лежит в пределах шума.

## Найденные ошибки измерения

Подробный разбор — в [`docs/REPORT.md`](docs/REPORT.md), здесь краткая сводка.

### 1. Ложный ноль на GQA-ru

Первая версия оценки дала Exact Match = 0.000 у базовой модели при опубликованных
46.37 — и при этом разумные 0.630 на MMBench-ru. Причина: после `trainer.train()` модель
осталась в режиме `train()` с активным gradient checkpointing, из-за чего отключался
KV-кэш, а `pixel_values` передавались в forward только на первом шаге генерации. Начиная
со второго токена изображение исчезало из контекста, и валиден был только первый токен.
MMBench требует одну букву и потому «выжил», GQA требует целое слово и развалился в ноль.

Исправление — три строки перед оценкой:

```python
model.eval()
model.gradient_checkpointing_disable()
model.config.use_cache = True
```

| | до фикса | после фикса |
|---|---|---|
| GQA-ru EM, база | 0.000 | 0.354 |
| GQA-ru EM, LoRA | 0.005 | 0.379 |

### 2. Смешивающий фактор (confounder) — формат промпта

Вторая ошибка опаснее первой: она не ломала пайплайн, а давала правдоподобный
положительный результат (+9.9 п.п., p < 10⁻⁹). Контрольный эксперимент показал, что
эффект держался на отсутствии `<bos>` в промпте базовой модели.

**Вывод для методики:** при сравнении базовой и дообученной модели формат промпта нужно
измерять как отдельный фактор. Адаптер неизбежно подстраивается под формат обучающих
данных, поэтому «родной» для него режим автоматически оказывается чужим для базы.

## Выводы

1. Пайплайн QLoRA-дообучения VLM полностью помещается в бесплатный Colab.
   Модель на 3B параметров в 4-bit, LoRA на 0.69% параметров, 4000 обучающих примеров —
   60 минут на Tesla T4. Полный свип оценки из 8 конфигураций — около часа.

2. **Дообучение не изменило точность модели в пределах разрешающей способности эксперимента.** Верхние границы доверительных интервалов ограничивают возможный эффект: он не превышает 3.0 п.п. на MMBench-ru и 1.2 п.п. на GQA-ru. То есть заметного прироста, ради которого стоило бы дообучать модель, здесь нет — а если какой-то эффект и существует, он мал. В корректном режиме промпта:
   GQA-ru −0.4 п.п. (p = 0.712), MMBench-ru +1.1 п.п. (p = 0.305). Это ожидаемо для
   `GQA-ru`, train-сплит которого базовая модель уже видела при instruction tuning.

3. **Дообучение дало устойчивость к формату промпта.** Базовая модель значимо зависит от
   наличия `<bos>` (+4.2 п.п. на GQA, +10.5 п.п. на MMBench), дообученная — нет (+1.3 и
   +1.7 п.п., оба не значимы). Это единственный статистически подтверждённый эффект
   адаптера.

4. **Основной методический результат — корректно измеренный пайплайн.** Найдены и
   устранены две ошибки измерения: баг генерации, занижавший метрику на GQA-ru с 35.4%
   до нуля, и смешивающий фактор формата промпта, из-за которого несуществующий прирост
   в 9.9 пункта выглядел статистически значимым. Вторая ошибка показательнее первой: она
   не проявляла себя ничем, кроме правдоподобного положительного результата.

## Ограничения

- **Числа MMBench не сопоставимы с опубликованными** — прямое следствие осознанно
  выбранного протокола разбора ответа (см. «Методика оценки»). Мягкий парсер отделяет
  понимание изображения от соблюдения формата, что необходимо для нашего исследовательского
  вопроса, но делает абсолютные значения непригодными для сравнения с лидербордом. Опора
  при чтении — базовый уровень случайного угадывания 26.65%. Строгая метрика при
  необходимости пересчитывается офлайн по сохранённым сырым ответам.
- **Базовая модель не воспроизводит опубликованное число.** В лучшем режиме (с BOS)
  получено 39.6% на GQA-ru против опубликованных 46.37%. Разрыв около 7 пунктов не
  объяснён полностью. Кандидаты: 4-bit квантование (авторы измеряли fp32), собственная
  конструкция промпта в `lmms-eval`, детали нормализации ответа, шум подвыборки ±3 п.п.
  Отдельно проверена и отклонена гипотеза о том, что чекпоинт обучался со стратегией
  `vision_feature_select_strategy = "full"` вопреки значению `default` в конфиге: замер
  на базовой модели (GQA-ru, n = 200, промпт с BOS) дал `default` 39.0% против `full`
  36.0%, разница −3.0 п.п. [−7.5; +1.5], p = 0.29. Верхняя граница интервала исключает
  выигрыш больше 1.5 п.п., то есть эта гипотеза не может объяснить семипунктовый разрыв.
- **Данные пересекаются с обучением базовой модели.** `GQA-ru` train использовался
  авторами `deepvk/llava-gemma-2b-lora` при instruction tuning.
- Использовано 10% train-сплита (4000 из 40 000) и 1 эпоха — 250 шагов оптимизатора.
- **Визуальный энкодер и проектор заморожены** — ошибки вида «лево/право» принципиально
  неустранимы этим методом.
- Оценка на подвыборке 1000 из 12 216 и 1000 из 3910.
- Нет валидационного сплита и отбора лучшего чекпоинта по валидации.

## Направления развития

1. Воспроизвести протокол `lmms-eval` и пересчитать на полных сплитах — это
   единственный способ получить числа, сопоставимые с опубликованными.
2. **Другая базовая модель.** `deepvk/llava-saiga-8b` (GQA-ru 51.44, MMBench-ru 56.65)
   заметно сильнее.
3. **Другие данные.** `deepvk/LLaVA-Instruct-ru` плюс данные в формате множественного
   выбора — формат MMBench в обучении не представлен вообще.
4. **Кэширование визуальных признаков.** Раз `vision_tower` и проектор заморожены, их
   выход детерминирован и может быть посчитан один раз на изображение — это убирает
   forward CLIP и препроцессинг картинок из каждого шага обучения.
5. **Целевая работа с бинарными вопросами** — на них приходится около четверти всех
   ошибок на GQA-ru.
